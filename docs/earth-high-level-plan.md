## 1. 产品方向

玩家成为整颗 Earth，在有限的太空场景中探索其他天体，通过短句、主动互动和可观察的变化，感受事物之间的关系。

Earth 仍是“万物之间”的第四种存在。它保留自由漫游、无计分、无胜负、无强制任务的定位，不扩展为需要经营、战斗或完成清单的独立游戏。

希望形成的体验循环：

```text
探索 → 注意到对象 → 接近与偶遇 → 自愿互动
     → 看见关系或环境的变化 → 带着新状态继续探索
```

并非每个天体都必须主动互动或改变世界。安静的景物与短句本身仍有价值；新增交互只应在能增强视角与关系感时引入。

### 已有天体清单：优先复用，避免重复建模

**除 Earth 外，已经有两个独立天体：月亮和有环星球。**严格分类时月亮是卫星，因此不是“已有两颗其他行星”。星环是有环星球的组成部分，不是第三个独立天体。

| 已有天体 | 源码标识与初始位置                                                              | 已有能力                                    | 后续处理                                                                        |
| -------- | ------------------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------- |
| 月亮     | `makeSpaceScene()` 内的 `moon`；`(80,5,-65)`；半径 `9`                          | 已有模型、材质和范围 `75` 的对白记录        | V1 在原对象上增加邀请与轨道，禁止另造一个“伙伴月亮”                             |
| 有环星球 | 同函数内 Group `p`，包含球体 `gas` 和星环 `ring`；`(-150,40,-230)`；球半径 `49` | 已有模型、材质、星环和范围 `290` 的对白记录 | V1 保留；未来若选择土星相关玩法，优先升级此对象，不再默认新增一颗相同用途的星球 |

上述标识是函数内局部变量，不是公开的场景注册 API。“有环星球”当前未正式命名为土星；命名与身份可另行确认，不能因为规划写了 Saturn 就重新建一套模型。现有 `w.sun` 是灯光引用，不是可以接近或对话的太阳物体。

源码位置、控制方式和数值见 [开发交接](prd-earth-handoff.md)。本计划不把未来能力写成当前架构。

## 3. 设计原则与优先级

1. **操作与发现清楚。** 玩家先能理解自己是什么、如何移动、哪里有可互动内容。
2. **每轮只验证一个完整变化。** 第一个候选是“邀请月亮后，它开始与 Earth 同行”。
3. **反馈和状态可信。** 操作有即时反馈，重复输入不复制物体，切换后能继续体验。
4. **画面支撑玩法。** Earth 的体积、轮廓、光影、构图和互动提示属于可读性基础，不因新增玩法被推迟到不可用。
5. **物理只提供表达。** 用简化轨道、光照与有限影响表达联系，不追求天文精度。
6. **不提前建设通用框架。** 先实现一个对象的实际需求，再从第二个不同案例中提炼复用部分。

此次提出以 Earth–Moon 作为首个玩法增量。它与此前“先打磨视觉与尺度转换”的建议存在优先顺序变化；接手开发者应在任务认领前确认本轮究竟先做视觉还是月亮玩法。两种方案都必须满足基本视觉可读性，本文不替项目方承诺顺序或追加全部功能。

## 4. 可逐步引入的玩法

| 能力           | 玩家可感知的变化                       | 所属阶段               |
| -------------- | -------------------------------------- | ---------------------- |
| 相遇与短句     | 接近对象时听见世界的回应               | 已有；继续沿用共享系统 |
| 结伴           | 一个原本独立的天体开始与 Earth 同行    | V1 候选                |
| 光照与外观变化 | 接近太阳后，Earth 的明暗或视觉状态改变 | V2 候选                |
| 有限物理影响   | 某个天体对运动或局部对象产生可控影响   | V3 探索                |
| 关系组合       | 既有伙伴改变后续相遇的结果             | V4 探索                |

“共享玩法词汇”表示一致的操作与反馈习惯，不代表全项目需要由 Earth 实现通用交互系统。

## 5. 迭代路线

| 阶段           | 范围与目标                                          | 完成条件                                   | 状态                         |
| -------------- | --------------------------------------------------- | ------------------------------------------ | ---------------------------- |
| 接入准备       | 明确 Earth 文件范围、输入路由、主循环接入和提示归属 | 共享负责人确认最小契约；不影响草层 E 操作  | V1 的前置依赖                |
| V1：第一次联系 | 升级已有月亮：可邀请、围绕 Earth 同行、保留会话状态 | 一个可发现、可主动完成、有持续结果的互动   | 唯一详细实施候选，见独立计划 |
| V2：光与能量   | 新增可见太阳，与结伴不同的光影/外观响应             | 玩家可辨认太阳作用；离开后状态恢复策略明确 | 可选后续，不列为 V1 要求     |
| V3：不同天体   | 从火星、木星或现有有环星球中选一个差异化机制        | 新对象确有新体验，并验证控制与性能成本     | 未来提案，不一次加入所有行星 |
| V4：关系组合   | 例如月亮与太阳共同产生一次有界视觉事件              | 至少一个依赖先前状态的可发现变化           | 等基础互动稳定后评估         |
| V5：更远处     | 星云、系外行星、双星、黑洞等                        | 由反馈重新确定问题与范围                   | 黑客松范围外                 |

V2 不要求同时引入“月亮也对太阳作出反应”；后者属于 V4 的组合能力，避免第二阶段同时承担两种新机制。

V3 的木星推拉或引力弹弓会影响共享移动规则，并非仅修改 Earth 模型即可完成。当前 Earth 位移由控制器直接更新，且限制在 X/Z 平面圆盘内；任何速度、受力或冲量方案均需单独协调。

每轮任务先标明“升级已有对象”或“新增天体”：V1 是升级月亮；有环星球/土星方向优先复用现有对象；可见太阳、火星和木星模型目前不存在，只有明确选择相应阶段后才评估新增。

### V2 光照的技术边界

当前 DirectionalLight 不会随距离自动衰减。若采用“越靠近太阳越亮”，需明确：可见太阳模型的位置、互动距离、受影响的灯光/材质、最大强度、变化速度及离开后的恢复方式。

可用 Three.js 材质和局部灯光实现初步效果；不默认新增后处理、物理库或外部资源加载。不要把灯光对象的存在等同于完整太阳玩法。

| 局部动画与视觉响应               | 唯一动画循环及世界更新回调                   |
| 使用缓存保存本页会话状态         | 跨世界生命周期、声音路由、存档与资源卸载策略 |

默认实现范围为 `src/worlds/space.js`。需要新建 Earth 专用文件时明确清单；其他三个世界、共享工具、依赖、原型、引擎和 CI 不作为顺手修改范围。

共享接口接入应先检查调用方，按 [架构决策模板](decisions/template.md) 记录实际方案。当前没有已批准的通用回调 API；下面的 V1 文档只提出必要能力，不宣称接口已经存在。

### 相遇概率的独立边界

- 继续使用 `world.talkers` 提供可遇见对象与对白。
- Earth 不实现第二套随机触发计时器，不增加无人消费的概率字段。
- 外部参数究竟控制对象出现、自动对白还是单位时间相遇率，由共享负责人定义。
- 建议将玩家主动邀请与随机对白分开：实际存在、符合资格的月亮可被邀请，不必等它随机说话。最终语义由双方确认，避免绕过共享策略。
- 若策略控制对象是否存在，Earth 只对实际存在且允许互动的对象显示邀请，不能生成一个额外“必遇月亮”来绕过配置。

## 7. 演示交付门槛

| 门槛       | 必须看到的结果                                        |
| ---------- | ----------------------------------------------------- |
| 接入可用   | 输入、提示、动画由共享入口驱动，其他世界行为保留      |
| V1 完整    | 玩家发现月亮、邀请成功、看见同行，切换后状态仍在      |
| 质量可审阅 | 基本光影/构图清楚；自动检查、针对性验证与人工记录完整 |
| 后续扩展   | 只有 V1 稳定且有剩余时间时，才评估太阳或一个新机制    |

“进入 Earth 后约 30 秒体验到一次有意义互动”是试玩目标，不能通过改变全局概率、强制弹出对白或替玩家完成邀请来达成。记录测试所用配置、设备、玩家路径和游戏时间/真实时间差异。

“无明显性能下降”必须有同设备前后数据才可判断。建议演示电脑先争取稳定 30 FPS；具体采样方式与允许回退幅度在基线测量后约定，不能把目标写成已达成事实。

## 8. 暂缓范围

V1 不包含太阳、其他新行星、引力、弹弓、连锁互动、伙伴解散、多伙伴管理、账号、存档、多人、实时 AI 对话、摄像头手势、移动端控制或真实物理引擎。未来阶段不默认升级为此次必做项。

公开链接、演示视频和离线备份仍是全项目交付事项，由对应负责人推进，不转移给 Earth 局部开发。

## 9. 接手前需明确的决定

1. 本轮先做视觉增量，还是进入 V1 月亮结伴；范围与截止时间由项目方给出。
2. 共享输入、提示和动画接入由谁负责，何时可用；当前不能假设已有接口。
3. 主动邀请与随机对白的关系，以及外部相遇参数的真实语义。
4. 演示设备、基线性能、取证路径和最低验收标准。
